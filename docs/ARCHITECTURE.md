# ARCHITECTURE.md

*Synthetic Cement Plant Digital Twin + AI Optimization Platform — PRD v1.1.1*

> **Synthetic Demonstration · Decision Support Only · Not validated against real plant data**

This document describes how the code is arranged and *why* the seams are where they are. It is a map
for someone about to change something, not a tutorial. Every claim below carries a `file.py:line`
anchor; where a design is deliberate and looks like a defect, it says so explicitly.

---

## 1. The one-line summary

A seeded physics simulation produces plant data; ML and optimization layers consume it; a single
abstract `DataProvider` stands between all of that and the dashboard, so that the dashboard cannot
tell — and must not care — whether the numbers came from a simulation or from a plant.

```
configs/*.yaml ──> src/simulation/ + src/process_models/   physics, delays, sensors
                            │
                            ▼
                   src/data_generation/ ──> src/data_processing/   datasets + FR-13 quality report
                            │
                            ▼
        src/features/ ──> src/models/ (A)  src/anomaly_detection/ (B)  src/optimization/ (C)
                            │
                            ▼
        ┌───────────────────────────────────────────────────────────┐
        │  src/digital_twin/provider.py :: DataProvider  (15 methods) │   <-- the seam
        └───────────────────────────────────────────────────────────┘
             ▲                                   ▲
   SyntheticDataProvider                RealPlantDataProvider
   (synthetic.py, complete)             (real_plant.py, 14 methods raise)
                            │
                            ▼
              src/digital_twin/session.py   application / domain services
                            │
                            ▼
              src/digital_twin/state.py     view registry + view models
                            │
                            ▼
              src/visualization/ + app.py   rendering, one self-contained HTML file
```

`src/digital_twin/session.py:3-8` states the required dependency direction verbatim (directive item
21):

```
DataProvider  ->  Application / Domain Services  ->  Digital Twin / ML / Optimization
                              |
                              v
                    Dashboard API / State  ->  Visualization
```

Nothing above the provider imports a process model, a trained estimator or an optimizer. That is not
an aspiration; it is what makes the real-plant swap a one-class change (FR-14).

## 2. The provider seam

`DataProvider` (`src/digital_twin/provider.py`) is an ABC with **15 abstract methods**
(`provider.py:65-145`) plus optional clock-control hooks (`:147-184`). Two implementations exist:

| | `SyntheticDataProvider` | `RealPlantDataProvider` |
|---|---|---|
| File | `src/digital_twin/synthetic.py` (1535 lines) | `src/digital_twin/real_plant.py` (376 lines) |
| Status | complete — every number from the PRD §11 simulation | **stub** — 14 of 15 methods raise `NotImplementedError` |
| `capabilities()` | reports what this session can serve | every field `False`, `missing` lists 13 names (`real_plant.py:151-176`) |
| Purpose | the demonstration | the documented shape of the future adapter |

Three properties make the seam load-bearing rather than decorative:

**Capability negotiation, not exception handling.** A view asks `capabilities()` *first* and degrades
the panels it cannot fill. `CapabilityError` is a `NotImplementedError` subclass (`provider.py:50`)
precisely so a caller that skipped the negotiation still fails in a catchable, named way rather than
with an `AttributeError`. `real_plant.py:139-150` explains why the stub answers this one method
instead of refusing it too: "a stub that refused here too would force the caller into a try/except
around every single call".

**Refusals that teach.** Every raising method's message is generated by `_todo()`
(`real_plant.py:79-98`) and names what would have to be built, the PRD section governing it, and the
recalibration that must follow. Those messages are the source text for
`docs/FACTORY_DATA_REQUIREMENTS.md` §4 — the requirements document quotes the code rather than
paraphrasing it, and `real_plant.py:71` points back at the document.

**Resampling that refuses to invent.** `RESAMPLE_RULES` is `("1s","5s","10s","30s","1min","5min")`
(`provider.py:42`), and `check_resample` (`:188-206`) rejects any rule finer than the source's own
interval because "upsampling would invent samples that were never measured". A real historian export
at 5-minute resolution therefore produces a refusal, not a smooth line.

**Lazy heavy import.** `src/digital_twin/__init__.py:53-66` exports `SyntheticDataProvider` via PEP
562 lazy attribute lookup. The reasoning is in its docstring: importing the implementation pulls in
process models, trained models and the optimizer, and "if the light layer could not be imported
without the heavy one, 'the UI depends only on the abstraction' would be true in the type signatures
and false in the import graph".

## 3. Four provenance channels

Directive item 1 requires the payload to keep four sources apart. `src/digital_twin/provenance.py:3-14`
declares them:

| Member | Meaning | Source |
|---|---|---|
| `OBSERVED` | what an instrument would report, sensor model applied | PRD §11.5 |
| `TRUTH` | the simulator's own noise-free state — **synthetic only** | PRD §11.2 |
| `PREDICTION` | Model A output | PRD §13.1 |
| `RECOMMENDATION` | Model C output | PRD §14 |

`CONFIGURATION` is a fifth enum member but **not** a data source: it marks static engineering metadata
(a unit, a documented range, a configured target). `DATA_SOURCES` (`provenance.py:41-46`) is exactly
the four.

The rule is enforced, not documented: the `no_mixed_provenance` test asserts that no payload channel
carries two of the four data sources at once and that every displayed number carries one of the five;
`state.py:949` exposes a `mixed_channels` audit for it.

`Value` is "the only object the UI is allowed to render as a number" (`provenance.py:16-18`). It
arrives carrying its unit, its documented range, its status and the call that produced it, "so a panel
never has to know a limit and can never hold a literal" — which is how NFR-6/AC-12 (no hard-coded
display value) is satisfied structurally rather than by review.

**Consequence for a real plant:** `TRUTH` has no real-world counterpart. A plant has instruments and
lab results; it has no noise-free ground truth. `RealPlantDataProvider.get_truth_state` is therefore
the one refusal that is *permanent* rather than pending — the truth-vs-observed comparison panel is a
synthetic-only capability by construction.

## 4. Uncertainty, labels and the words that cannot change

`src/labels.py` holds the fixed vocabulary. It is a module rather than a set of string literals so
that no view can soften the wording locally.

- **Uncertainty is a spread, never a percentage.** Predictions carry an ensemble spread on `Value`;
  recommendation confidence is the categorical `HIGH` / `MEDIUM` / `LOW`
  (`labels.py:120-146`). `src/digital_twin/insights.py:8-11` records the invariant directly: "there is
  no confidence-percentage field anywhere (FR-23, AC-18)".
- **No control vocabulary.** "Automatic Control Command" is forbidden system-wide
  (`labels.py:33`, FR-16, PRD §30); outputs are "AI Recommendation" under "Decision Support Only"
  (`labels.py:29-30`).
- **Savings are simulated.** `labels.py:75` — "Simulated saving from a synthetic model - not a
  guaranteed real-world saving".
- **Inconclusive is a first-class answer.** `EVIDENCE_INCONCLUSIVE_LABEL` (`labels.py:83`) is what a
  detector reports when its evidence does not separate the readings — the standard case for sensor
  drift. Likewise `NO_SAFE_RECOMMENDATION` (`labels.py:70`): constraints are never relaxed to
  manufacture advice.
- **Envelope state is displayed.** `OUTSIDE_ENVELOPE` (`labels.py:59`) marks an operating point beyond
  what the models were fitted for.
- **Model absence is displayed.** `MODEL_UNAVAILABLE_STATEMENT` (`labels.py:101-105`) — "the panel
  shows no number rather than a substitute one".

## 5. Presentation constants live in YAML, marked `ASSUMPTION`

`src/digital_twin/settings.py:1-16` is a typed reader for `configs/dashboard.yaml` and holds
"presentation constants only … Nothing here is a process quantity." The separation is strict:

| Kind of number | Where it lives |
|---|---|
| Process ranges and units | `src/schema.py` |
| Process limits / constraints | `configs/kiln_dynamics.yaml`, `configs/mill_dynamics.yaml` |
| Model thresholds | `configs/ml.yaml`, `configs/optimization.yaml` |
| Display and animation numbers | `configs/dashboard.yaml` |
| Plant tag names (when a plant exists) | `configs/tag_mapping.yaml` — and *only* names |

`configs/tag_mapping.yaml:22-26` explains the last row: a mapping file that also carried ranges "would
give a plant two contradictory authorities for the same band".

Every numeric in `configs/dashboard.yaml` is tagged `ASSUMPTION`, and `settings.py:8-10` gives the
reason it is a module at all: "a panel may not hold a literal number, so the panel reads
`settings.animation.particles` and the number exists exactly once, in the YAML".

`AnimationSettings.scale` is "the single function that turns a process fraction into an animation
parameter" (`settings.py:12-15`), which is how AC-21 ("every animated element is driven by live
state") holds by construction: an animation parameter is `scale(pair, value.fraction_of_range())` and
there is no other route to one.

## 6. The view registry and the payload→render split

`src/digital_twin/state.py` is "the Dashboard API / State layer" and its "single job is to turn what a
provider can answer into the ten *view models* the dashboard draws — one per screen A-J — **without
emitting a byte of HTML**" (`state.py:1-9`).

`VIEWS` (`state.py:76-87`) is the registry: each row is `(view_id, method_key, title, subtitle)`, so
`DashboardState.view()` dispatches on either the directive's `A`–`J` id or the method name, and titles
live in one place rather than restated per method.

| id | key | screen |
|---|---|---|
| A | `overview` | Plant Overview |
| B | `kiln_twin` | Kiln Digital Twin *(rendered)* |
| C | `kiln_process` | Preheater & Kiln |
| D | `clinker_cooler` | Clinker Cooler |
| E | `mill_twin` | Cement Mill Digital Twin *(rendered)* |
| F | `mill_separator` | Mill & Separator |
| G | `energy` | Energy Monitoring |
| H | `intelligence` | AI Prediction & Anomaly |
| I | `what_if` | What-If Simulation |
| J | `optimization` | AI Optimization — "Decision support only — the system writes no setpoint" |

**Two of ten screens have a renderer.** `app.py:62-68` duck-types the twin views on the two fields
`TwinView` adds (`line` and `snapshot`) and sends those to `svg_twin.render_twin`; everything else goes
through `_payload_html` (`app.py:81-93`), which prints the frozen view model as JSON under the label
"View-model payload (no renderer for this screen yet)". Its docstring states the intent: "Phase 6D owns
the per-view renderers. Until they exist this host shows the frozen view model verbatim **rather than a
prettier screen built from values it made up**."

This is the single most important thing to understand before "finishing" the dashboard: the eight
payload screens are not unimplemented data, they are unimplemented *pixels*. The numbers exist, are
validated and are asserted against in tests; only the drawing is missing. Adding a renderer must not
add a number — a renderer may only read a view model (`state.py:7-9`).

A view that raises is re-raised as a `RuntimeError` naming the screen and "is never replaced by a
placeholder number" (`app.py:113-114`).

### Frame coherence

`state.py:35-39` explains why the current snapshot, equipment, KPIs and regime are fetched **once** per
frame into a `_Frame` shared by all ten views: "two reads of a noisy sensor channel could disagree, and
a dashboard drawn from disagreeing reads is not one dashboard." Model outputs and trends are per-view,
because each is its own answer with its own timestamp.

### Degradation vs. hard blocking

`_history` (`state.py:531-541`) checks `capabilities().history` and returns `()` when it is false —
clean degradation. But `_Frame` construction (`state.py:544-552`) calls `get_current_state`,
`get_equipment_status`, `get_kpis` and `get_operating_regime` **unguarded** (`:547-550`), and
`Clock.__init__` reaches `provider.get_current_state().timestamp` unconditionally
(`src/visualization/clock.py:140-141`). Verified empirically: a `DashboardState` cannot currently be
constructed around `RealPlantDataProvider` at all — it raises before any view is requested. The
capability contract is honoured for the optional surfaces and not yet for the four mandatory ones.
This is a real gap, recorded here rather than smoothed over; it is also documented from the data side
in `docs/FACTORY_DATA_REQUIREMENTS.md` §4.3.

## 7. Deliberate designs that look like defects

Change any of these only with a reason that beats the reason recorded here.

**The `visualization.clock` layering smell.** `src/digital_twin/state.py:68` imports
`src.visualization.clock`, while `src/visualization/clock.py:42-44` imports from
`src.digital_twin.payloads` / `.provider` / `.settings`. Read as a package graph that is a cycle, and
it reads oddly against §1's downward flow. The **module** import graph is acyclic and no reachable
`ImportError` exists — `clock.py` depends only on the light contract modules, never on
`digital_twin.state`. It is a layering smell, not a bug. **Do not "fix" it** by moving `Clock`; the
cure (a fifth package, or a duplicated clock) costs more than the smell.

**`src/digital_twin/synthetic.py` is 1535 lines and is not split.** The provider implementation is
deliberately one module: splitting it would scatter the fifteen contract methods across files whose
boundaries would not match the contract's. This is a standing project constraint, not an oversight.

**`configs/tag_mapping.yaml` is empty.** `sources: {}` (`:80`) is the *specified* v1.1 state
(PRD §26.2, "not yet populated"). Its own header explains why an example is not given a plant-like
name: "a placeholder that reads like a real tag is the failure mode this file is guarding against"
(`:61-63`). Populating it with invented tags "would look like a plant had been onboarded when none has"
(`:16-20`).

**Fourteen methods that raise.** `RealPlantDataProvider` is more useful raising than absent: it proves
the contract is satisfiable by a non-synthetic source, it gives the dashboard a named refusal instead
of an import error, and each message is the requirement text for the adapter that will replace it.

**`configs/dashboard.yaml: presentation.refresh_seconds` has no consumer.** It is parsed and validated
(`src/digital_twin/settings.py:257, 303-304`) and echoed by `describe()` (`:351`), but nothing drives
anything from it — the presentation loop it describes belongs to Factory Presentation Mode (PRD §29),
which is not implemented. Noted so it is not mistaken for a live setting.

**`alarm_fraction_of_span: 0.0`** (`configs/dashboard.yaml:25`) means the alarm band is the documented
range boundary itself, with the amber band at `warn_fraction_of_span: 0.10` inside it. Both are
`ASSUMPTION`s about *display*, not process alarm limits.

## 8. Where the layers are, by file

| Layer | Files | Notes |
|---|---|---|
| Contract | `src/digital_twin/provider.py`, `payloads.py`, `provenance.py`, `settings.py` | light; importable without the model stack |
| Providers | `synthetic.py`, `real_plant.py` | `synthetic.py` exported lazily |
| Application / domain | `session.py`, `scenario_driver.py` | `session.py` is "the *only* place that knows how the four validated layers of Tasks #2-#5 are wired together" (`session.py:10-15`) |
| Dashboard API / state | `state.py`, `layout.py`, `insights.py` | `layout.py` declares which tags each panel shows; it writes no number |
| Visualization | `src/visualization/svg_twin.py`, `charts.py`, `theme.py`, `clock.py` | self-contained HTML/CSS/SVG; no external assets |
| Host | `app.py` | CLI, document assembly, per-view timings via `time.perf_counter` |

Two constraints worth restating because they are easy to break:

- `session.py` **trains nothing and changes no model** (`session.py:19-24`). Model A is *loaded* from
  `models/registry.json`; Model B is fitted with its own defaults on the chronological training
  fraction — "No threshold, weight, range or objective is touched."
- `scenario_driver.py` is "deliberately *thin*" (`:4-14`): setpoints come from
  `ScenarioScheduler.step_variable`, physics from `PlantTwin.simulation_step`, health from
  `EquipmentHealthProcess.health_at`, the observable channel from `SensorModel.apply`. "No process
  equation, limit or noise parameter is re-implemented here."

## 10. What this architecture does not give you

- **No plant connectivity.** No instrument is read; no setpoint is written; the system closes no loop.
- **No validated plant model.** Every engineering constant is an `ASSUMPTION`
  (`SIMULATION_ASSUMPTIONS.md`, NFR-8). PRD §21.3 lists "any claim of plant-specific calibration"
  among what the synthetic environment does *not* validate.
- **No numeric confidence.** Spread and category only (FR-23, AC-18).
- **No path from a tag mapping to a valid model.** Mapping makes data readable; PRD §21.4 puts
  quality assessment, recalibration, retraining, plant validation and operator validation between that
  and any believed number. See `docs/FACTORY_DATA_REQUIREMENTS.md` §7.
